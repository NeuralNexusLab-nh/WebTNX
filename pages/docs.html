02 · Forwarding

The complete HTTP envelope.

WebTNX forwards HTTP method, path, query parameters, request body, safe end-to-end headers, response status, response body, and safe response headers. Binary data stays binary through the encrypted envelope.

Hop-by-hop headers such as Connection, Transfer-Encoding, Host, and Content-Length are regenerated instead of copied. Browsers additionally prohibit JavaScript from setting headers such as Cookie; use a native client when exact header fidelity is required.

WebSocket, Server-Sent Events, and streaming responses are not currently supported.

03 · Security model

AES-256-GCM over TLS.

Registration creates a cryptographically random 256-bit agent token and independent 256-bit AES key. The token authenticates polling, keepalive, and response delivery. Request and response bodies are protected with AES-256-GCM, which provides confidentiality plus tamper detection.

TLS protects all control-plane metadata in transit. WebTNX is not described as end-to-end encrypted because the relay server decrypts response bodies before delivering them to the public visitor. Tunnel credentials are ephemeral and held in process memory.

Do not expose administrative services or sensitive localhost applications without their own authentication. A public tunnel URL remains public.

04 · Browser agent

CORS is continuously verified.

The browser agent checks http://localhost:PORT/ every four seconds. When CORS is blocked or the local service is offline, a persistent warning appears and disappears automatically after a successful check.

Access-Control-Allow-Origin: https://your-webtnx-host.example
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Allow-Methods: GET, POST, PUT, PATCH, DELETE, OPTIONS

Native clients do not use a browser and therefore do not require CORS.

05 · Resource limits

Guardrails for small servers.

  • Maximum request body: 2 MB.
  • Maximum response/control payload: approximately 2 MB before encoding.
  • Maximum 10 queued requests per tunnel, 64 pending requests, and a 4 MB queued-body budget per process.
  • Timeout range: 5–120 seconds.
  • Inactive tunnel sessions are removed from memory.

The relay uses in-memory queues; restarting the server ends all active tunnels. This avoids persistent storage of request headers and bodies.

06 · Self-hosting

One Node process.

git clone https://github.com/NeuralNexusLab-nh/WebTNX.git
cd WebTNX
npm ci
NODE_OPTIONS=--max-old-space-size=24 PORT=3000 node server.js

The heap cap is recommended for 50 MB-class instances. Set TRUST_PROXY=1 only when WebTNX is directly behind one trusted reverse proxy. This makes the logged source IP use the forwarded client address. Terminate HTTPS and enforce rate limits at that trusted proxy.
